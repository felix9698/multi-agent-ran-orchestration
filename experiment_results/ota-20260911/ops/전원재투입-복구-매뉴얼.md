## 1. 반드시 알아야 할 인과 사슬

> **먼저 읽어라 (2026-09-21 정정).** 아래 사슬은 전부 **증상**이다. 그날의 진짜 근본원인은
> enb2 와 PC1 의 `docker0` 가 둘 다 `172.17.0.1` 이어서 SCTP 멀티호밍이 그 주소를 광고하고,
> PC1 이 자기 주소를 주장하는 association 을 3초 만에 ABORT 한 것이었다(**6장**).
> 원격 기지국만 E2 가 안 붙으면 **6장을 먼저** 하고, 그게 통과할 때만 아래를 본다.


이 베드가 전원 재투입 뒤 안 도는 이유는 거의 항상 아래 **한 사슬**이다.
증상은 맨 끝에서 보이지만 원인은 맨 앞에 있다.

```
gnb2 의 X310 이 스트리밍 시작 직후 간헐적으로 끊긴다
   (uhd::io_error: socket closed — 2026-09-21 기준 기동 3회 중 1회)
        ↓  그때 gNB 는 이미 E2 등록을 마친 상태다
RIC 의 노드→소켓 맵에 죽은 포트가 남는다
   (RIC 은 재등록해도 옛 sockaddr 를 버리지 않는다)
        ↓  패킷: RIC:36421 → gnb2:58100 [INIT] / gnb2 → [ABORT]
그 노드로 가는 구독이 영영 응답을 못 받는다
        ↓
KPM 게이트가 4번째 구독(첫 gnb2 구독)에서
   "Timeout waiting for Report. Connection lost with the RIC?" 로 죽는다
        ↓  죽은 게이트의 구독 6개는 **gnb1 안에** 남는다
gnb1 이 그 번호로 계속 지시를 올리고, RIC 로그에
   "RIC Indication ... but no xApp associated" 가 쏟아진다
        ↓  그걸 처리하느라 RIC 의 E2 SETUP 응답이 3초를 넘기면
gnb2 가 기동 중 즉사한다
   e2_agent.c:225  assert(bi_map_size(&ag->pending) == 1)
        ↓
처음으로 돌아간다 (자기 복제 고리)
```

### `pend_event` assert 의 기전 (소스)
- `e2_agent.c:474-481` — SETUP 요청을 보내며 **3초 주기** 타이머를 걸고 pending 에 1건 넣음
- `msg_handler_agent.c:310-321` — SETUP 응답이 오면 그 항목을 빼고 타이머 fd 를 poll 에서 제거
- `e2_agent.c:225` — 타이머가 울릴 때 **맵 크기가 정확히 1**이라고 단정

응답이 3초 근처에 오면 타이머 이벤트가 이미 큐에 들어온 뒤라, 맵이 빈 채로
디스패치되어 assert 가 깨진다. **RIC 이 느리면 기지국이 죽는다**는 뜻이다.

### 두 사망을 가르는 법 (중요)
```bash
ssh enb2 'for L in $(ls -t /tmp/gnb2-probe-*.log | head -5); do
  printf "%-42s pend=%s  E2등록=%s  끝=%s\n" "$(basename $L)" \
    "$(grep -ac pend_event $L)" "$(grep -ac "E2 SETUP RESPONSE rx" $L)" \
    "$(tail -1 $L | cut -c1-40)"; done'
```
- `pend_event` assert → **E2 등록 0** → RIC 맵을 더럽히지 않는다. 그냥 다시 띄우면 된다.
- `socket closed` → **E2 등록 1** → **RIC 맵에 죽은 소켓이 남는다. RIC 을 반드시 재시작해야 한다.**

## 3. 프로듀서가 거부할 때

프로듀서는 **자기가 쓰는 파일이 배포 당시 그대로인지** 해시로 확인한다.
읽는 설정은 번들이 아니라 `~/oran-deploy/session-20260819/lower-live/live-flexric.json` 이다.

```bash
python3 - <<'PY'
import hashlib, json, os
p="/opt/ran-lab/controller/oran-deploy/session-20260819/lower-live/live-flexric.json"
cfg=json.load(open(p)); base=os.path.dirname(p)
sha=lambda q: hashlib.sha256(open(q,"rb").read()).hexdigest()
for k in ("backendReleaseManifest","capabilityManifest","e2CapabilityInventory"):
    v=cfg[k]; f=os.path.normpath(os.path.join(base, v["path"]))
    print(("일치 " if sha(f)==v["sha256"] else "불일치"), k, f)
PY
```

- `... does not match its digest` → 그 파일이 바뀐 것이다. `lower-live/` 의
  `*.before-*` 백업 중 **핀과 같은 해시**를 가진 것을 찾아 되돌린다.
- `connection witness differs from the active E2 inventory` → epoch 이 달라진 것이다.
  이건 **재핀이 할 일**이다. 손으로 고치지 마라.

## 4. 절대 하지 말 것 (전부 2026-09-21 에 실제로 한 실수)

- **봉인 파일을 손으로 고치지 마라.** 릴리스 무결성은 바이너리 → 빌드 매니페스트 →
  릴리스 매니페스트 → 라이브 바인딩으로 엮여 있고, 프로듀서는 **실행 중인 RIC 프로세스의
  `/proc/<pid>/exe` 해시**까지 대조한다. 한 줄을 고치면 네 곳이 어긋난다.
  원본 사본이 `~/a1p-stage/releases/...` 와 `~/a1p-stage/phase-b-recipient.*/...` 에 있으니
  **언제나 그 둘과 대조**해서 되돌려라. 내가 만든 백업은 이미 오염돼 있을 수 있다.
- **한 번에 두 가지 이상 바꾸지 마라.** 바이너리·설정·순서를 같이 바꾸면 무엇이 원인인지
  영영 모른다.
- **`pgrep -f <스크립트이름>` 으로 생존을 확인하지 마라** — 자기 명령줄을 매칭한다.
  `pgrep -af ... | grep -v eval` 을 쓰거나 **로그 파일이 자라는지**로 확인해라.
- **`docker logs --tail N` 으로 세지 마라** — 같은 컨테이너의 **이전 실행분까지** 센다.
  반드시 `--since <기간>` 을 써라.
- **재시도로 덮지 마라.** 세 번 똑같이 실패하면 그건 확률이 아니라 결정적 고장이다.

## 6. 원격 기지국만 E2 가 안 붙을 때 — 최소 재현기부터 (2026-09-21 에 5시간을 쓴 자리)

**증상**: gnb1(= RIC 과 같은 호스트)은 구독이 되는데 gnb2 만 4번째 구독에서
`Timeout waiting for Report` 로 게이트가 죽는다.

**절대 RIC·gNB 코드부터 보지 마라.** 아래 20줄로 **두 호스트 사이 SCTP 자체**를 먼저 잰다.

PC1 에서:
```python
import socket, time
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM, socket.IPPROTO_SCTP)
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("192.168.50.1", 37999)); s.listen(4); print("listen", flush=True)
c, a = s.accept(); print("accepted", a, flush=True)
t0 = time.time()
while time.time() - t0 < 75:
    print("rx %r at %.0fs" % (c.recv(64), time.time()-t0), flush=True)
```
enb2 에서 (바인드 **없이**):
```python
import socket, time
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM, socket.IPPROTO_SCTP)
s.connect(("192.168.50.1", 37999)); t0 = time.time()
for i in range(8):
    s.send(b"ping%d" % i); print("tx %d at %.0fs" % (i, time.time()-t0), flush=True); time.sleep(10)
```

| 결과 | 뜻 |
|---|---|
| 3~20초에 `Connection reset by peer` | **경로가 범인이다.** 아래로 계속 |
| 80초 완주 | SCTP 는 멀쩡하다. 그때서야 FlexRIC 을 본다 |

이어서 클라이언트에 `s.bind(("192.168.50.2", 0))` 한 줄을 넣어 **단일 주소만 광고**하게 한다.
- 이때 완주하면 → **SCTP 멀티호밍이 원인**이다.
- 상대 호스트의 주소를 **하나씩** 빼며(`sudo ip addr flush dev <iface>`) 범인을 가린다.
  후보: `docker0`, `tailscale0`, 무선, X310 서브넷. **한 번에 둘을 빼면 아무것도 못 배운다.**

**2026-09-21 의 범인은 `docker0` 였다** — enb2 와 PC1 이 둘 다 `172.17.0.1/16` 이었고,
상대가 "내 주소" 를 자기 것이라 광고하니 PC1 이 association 을 끊었다.
고친 방법: enb2 `/etc/docker/daemon.json` 에 `{"bip": "172.28.99.1/24"}` 후 `systemctl restart docker`.

**루프백 대조도 같이 해라** — PC1 안에서 127.0.0.1 로 같은 시험을 하면 호스트 스택의 무죄가
증명되고, 남는 건 경로뿐이다.

## 8. gNB2(다른 호스트)만 사용자 평면이 죽었을 때 — **raw 테이블부터 보라**

**증상**: UE 가 붙고 IP 도 받는데 `ping -I oaitun_ue1 <ext-dn>` 이 100% 실패한다.
**gnb1(UPF 와 같은 호스트)은 멀쩡하고 gnb2 만** 그렇다.

**2026-09-21 의 원인**: PC1 의 **raw 테이블**에
```
-A PREROUTING -d 192.168.70.134/32 ! -i demo-oai -j DROP
```
가 있어 enb2 에서 오는 GTP-U 가 UPF 에 **한 패킷도** 닿지 않았다.
`raw` 는 `filter`·`nat` 보다 **먼저** 처리되므로, FORWARD 규칙도 라우팅도 MASQUERADE 도
전부 정상으로 보인다. 이것 때문에 몇 시간을 버렸다.

**진단 (이 순서로, 각 한 줄)**

## 10. gNB 한 쪽만 "하향이 죽었다" 로 보일 때 (2026-09-21/22 전수 조사)

**먼저: 그것은 대개 하향 고장이 아니다.** gNB 가 상향 HARQ-ACK 를 못 들으면 하향 TB 를
끝까지 재전송하므로 하향 실패로 보인다. 아래 순서로 **상향부터** 의심하라.

### 통계를 믿기 전에 — RNTI 단위로 다시 세라

`dlsch_rounds 728/682/676/675` 같은 값은 **실패한 연결들이 섞인 누적값**이다.
2026-09-22 에 20분짜리 gnb1 로그 하나에 **RNTI 647개**가 있었고 전부 붙으려다 실패한
흔적이었다. 아무 RNTI 의 값을 읽고 "하향이 93% 실패한다" 고 쓰면 안 된다.

```bash
# RNTI 별 마지막 통계만 뽑기 (누적 오염 제거)
python3 - "$(ls -t /opt/ran-lab/controller/gnb1-loop38-*.log | head -1)" <<'PY'
import sys, re
last, order = {}, []
for line in open(sys.argv[1], 'rb'):
    t = line.decode('utf8', 'replace')
    m = re.search(r'UE ([0-9a-f]{4}):', t)
    if not m: continue
    if m.group(1) not in last: order.append(m.group(1))
    for k, v in re.findall(r'(dlsch_rounds|MCS|CCE fail)\s+([0-9/]+)', t):
        last.setdefault(m.group(1), {})[k] = v
print(f"RNTI {len(order)}개")
for r in order[-5:]: print(' ', r, last[r])
PY
```

### 유령 간섭인지 우리 UE 인지 — 1분이면 갈린다

**그 셀에 UE 를 하나도 배정하지 않고** RA 검출을 센다. 0 건이면 유령이 아니라 우리 UE 다.

```bash
L=$(ls -t /opt/ran-lab/controller/gnb1-loop38-*.log | head -1); sz=$(stat -c %s "$L")
sleep 60; tail -c +$((sz+1)) "$L" | grep -acE 'Initiating RA procedure|RA-RNTI'
```

### 전력 드리프트는 **네 칸짜리 가족**이다 — 하나만 고치면 안 된다

2026-09-22 에 gnb1 이 gnb2 대비 전부 낮았다. 하나씩 고치다 두 번 놓쳤다.

| 파라미터 | 역할 | 효과 |
|---|---|---|
| `p0_NominalWithGrant` | PUSCH 수신목표 | 맞추자 부착 성공 |
| `p0_nominal` | **PUCCH** (conf 에서 `pucchGroupHopping` 뒤) | 단독으론 변화 없음 |
| `preambleReceivedTargetPower` | **Msg3 전력이 여기서 파생된다** | Msg3 실패 **90% → 77%** |
| `powerRampingStep` | 상승 폭 | gnb2 와 같게 했더니 **악화(100%)** → 되돌려 **55%** |

**PRACH 는 통과하는데 Msg3 만 죽으면 `preambleReceivedTargetPower` 를 보라.**
그리고 **같게 맞추는 것이 언제나 옳지는 않다** — 지표가 반대로 움직이면 되돌린다.

### 에너지 문턱으로 유령을 가르는 방법은 **그날만** 유효하다

2026-09-16 에는 실패 RA 43~48 dB · 성공 51~56 dB 로 빈 띠가 있어 `prach_dtx_threshold`
로 갈랐다. 2026-09-22 에는 실패 51.0~55.7(중앙 52.7) · 성공 51.0~56.4(중앙 52.7)로
**완전히 겹쳐** 문턱으로는 손댈 수 없었다. **매번 다시 재라.**

### 코어를 의심하기 전에 — 패킷으로 닫아라

설정 확인만으로는 부족하다. **세션 중에 GTP-U 가 실제로 그 gNB 에 도착하는지** 잡아라.

→ 코어·터널·방화벽·세션 전부 결백. 손실은 **gNB 의 GTP-U 입력과 UE 사이**다.
같이 본 지표: UPF 오류 0건, SMF `PDU Session Establishment Accept` 20건·N4 전부 응답,

### 마지막에 남는 것
